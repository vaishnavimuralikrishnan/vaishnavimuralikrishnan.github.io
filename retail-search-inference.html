What Reranking Costs and What It Buys

A cross-encoder reranker is the standard way to improve a semantic search ranking, and it is also the most expensive component in the path. I built a benchmark to measure what it buys per unit of inference cost on Amazon ESCI. On this workload, the measured quality gain is not statistically supported, and the cost is a 6.6 to 20.6 times increase in median latency.

Workload: 200 test queries, 4,103 judged query-product pairs, CPU inference Models: MiniLM-L6 bi-encoder and MS MARCO MiniLM-L6 cross-encoder Evaluation: NDCG@10, exact-match recall, paired bootstrap
01

The Engineering Question

A search ranking pipeline usually has a cheap first stage and an expensive second stage. A bi-encoder embeds the query and compares it against precomputed product vectors, which costs one query encoding and a matrix product. A cross-encoder reads every query and product pair jointly through a transformer, so its cost grows with the number of pairs scored. Selective reranking limits that cost by applying the cross-encoder only to the top K semantic candidates.

The decision to deploy a reranker is a trade-off between ranking quality and inference cost, and it should be made with measurements rather than convention. This project quantifies both sides under one fixed workload and reports how certain each conclusion is. Selective reranking is an established technique and is not presented here as new. The contribution is the measurement discipline.

Scope: every method ranks a supplied candidate set, namely the products that ESCI annotators judged for each query. There is no catalogue-wide retrieval stage, so the results describe reranking over small judged pools and not end-to-end search quality.

Candidates outside the top K keep their semantic order after the reranked head. Semantic similarities and cross-encoder logits live on different scales and are never compared or fused, so the final order is defined by a single rule: reranked head first, semantic tail second.

03

Evaluation Design

The benchmark uses the Amazon ESCI shopping-queries dataset, Task 1, US locale. Relevance labels are mapped to graded gains (Exact = 3, Substitute = 2, Complement = 1, Irrelevant = 0). The evaluation sample is 200 test queries drawn with a fixed seed of 42, which keeps each query's full candidate set: 4,103 query-product pairs, about 20.5 per query, ranging from 9 to 55.

Every method is evaluated on the same queries with one metric implementation. NDCG@10 uses the graded gain with a log2 discount. Ties are resolved by stable sorting, so equal scores keep dataset order. Exact-match recall is the share of queries with at least one Exact product in the top 5 or top 10. Uncertainty is estimated with a paired bootstrap that resamples queries, not rows, because the rows within a query are not independent.

Earlier exploratory runs used a different query sample. They were removed from the benchmark so that old and new numbers are never compared as evidence of improvement.

A property of the workload

With about 20 candidates per query, K=20 already scores 81% of all pairs and K=30 scores 91%. On pools this small, increasing K approaches the cost of reranking everything without a corresponding quality gain. The cost curve is bounded by pool size, which is a limit of this benchmark and not a general property of selective reranking.

Exact-match recall in the top 10 was 0.99 for semantic-only ranking and for every selective configuration. Exact recall in the top 5 fell from 0.940 to 0.915 at K=20 and K=30. That change was observed on one sample and was not tested for significance.

What this establishes

The observed differences are within sampling noise. The data neither supports a quality improvement from reranking nor rules out a small one: the intervals extend to roughly +0.015 NDCG@10, so an effect of that size could exist and this sample is too small to detect it. The supported statement is that semantic-only ranking is a strong default on this workload.

07

Engineering Decisions

Separate offline index from online inference

Product titles are encoded once into a normalised float32 matrix with a title-to-row mapping. The index is cached with a checksum and reused only when the model, the title list and the matrix all match. The query path never encodes product titles: a candidate that is absent from the index raises an error instead of silently adding latency.

One ranking policy for evaluation and service

The selective reranking function is shared by the offline evaluation and by search_candidates(), which returns the ranked rows together with candidate count, reranked count, and separate timings for query encoding, semantic scoring and reranking. A test compares the service output against the evaluation orderings, so the benchmark describes the code that would serve queries.

A single metric implementation

NDCG@10 is computed by one function that is checked against a reference implementation on synthetic cases. Every method is converted to an explicit stable ordering before scoring, which removes tie-handling differences between methods as a source of apparent gains.

08

Limitations and Next Steps

The service ranks a supplied candidate set and does not retrieve from a catalogue. The results rest on one sample of 200 queries with about 20 candidates each, one seed, and sequential CPU timings. BM25 is fitted per query on its candidate titles, so it is a weak baseline and not a tuned one. The cross-encoder is used as released and was not adapted to ESCI. This is not a production system: there is no concurrency handling, request batching or monitoring.

The next step that would change what the benchmark can conclude is an independent retrieval stage over the indexed catalogue, which produces candidate pools of realistic size and gives selective reranking a regime in which K matters. A second step is repeating the evaluation across several seeds to test whether the intervals are stable.
